# Thesis tracker UX review

Reviewed on 2026-10-02. The design target is a simple, utilitarian tool for one regular user. The user's stated priority is **opening a student and recording meeting notes**. The recommended direction is a compact student list with a stable notes workspace, short labels, plain surfaces, and explanatory copy only where it changes a decision.

An [interactive concept](./ux/utilitarian-concept.html) illustrates this direction with sample data. Open the HTML file in a browser. Search, filter, open students, switch between drafts, and save a demo note. Its data and drafts live in memory and reset on reload; it does not connect to the application. It covers the student-and-notes workflow, rather than every application screen.

## Implementation status — 7 October 2026

The approved student-and-notes design is implemented in the application: compact cohort rows, collapsed secondary filters, a side-by-side workspace on wide screens, and a focused student view with a return action below 1100 px. Latest discussion and next actions precede an immediately available note form. Detail editing, earlier notes, phase history, and archive/restore actions use simple disclosures. Shared surfaces now use flat backgrounds, small corners, and stronger muted-text contrast.

Drafts for both notes and student edits survive switching, closing/reopening, browser history, and failed saves within the current page. Leaving or reloading prompts before discarding changes. Drafts are held in memory and do not survive a reload. Saving clears only the saved form's draft. Follow-up explicitly keeps, clears, or sets the meeting; keeping does not write a stale meeting value back to the database. New note timestamps default to the student's booked meeting time in the configured app timezone, or the recording time when no meeting is booked. The `Past MSc target` filter excludes submitted students and future targets, and empty search results offer a reset.

The remaining follow-up is settings navigation and observing task completion in regular use. The findings below describe the pre-redesign app; the separate HTML concept remains the approved reference. For the timestamp default, the current behavior above supersedes the recording-time proposal below.

## Method and scope

This pass combines a hands-on workflow review, inspection of the rendering and interaction code, and desk research from Nielsen Norman Group, GOV.UK, and W3C. It is an expert review, not a usability study with measured user task times. The user's preference establishes the workflow priority; the proposed layout still needs validation during actual supervision work.

The app ran against an isolated local D1 database containing eight sample students and seven meeting logs. The review covered login, the list, phase and Gantt views, student selection, note entry, search and filtering, the calendar setup state, and data tools. Desktop observations used a 1440 × 900 CSS-pixel viewport; mobile observations used a 390 × 844 emulated viewport. Calendar invitations were assessed from code; a live connected Google Calendar was not exercised. No production data or application behavior was changed.

## Findings and priorities

Priority reflects the stated notes workflow. Observations are reproducible in the reviewed app; their effect on the user's speed is a hypothesis until tried in real work.

| Next     | **Meeting defaults can misrepresent the note.** On 2 October, Emma's new log defaults to her upcoming meeting on 5 October. A blank follow-up clears the saved meeting. The desktop list currently omits the explicit meeting-status labels shown on mobile. An overdue date looks like an ordinary date. In the proposed list, place a short `Overdue` or `Not booked` state next to the meeting information so urgency does not require date arithmetic. Keep submitted records out of attention-oriented filters; a missing meeting on a submitted thesis is not automatically a problem.

## Recommended notes workflow

1. Search or scan the student list. Keep name, phase, and next meeting visible; put long thesis topics, profile notes, and log counts in the student workspace.
2. Open the student once. Show their latest discussion and agreed actions immediately, followed by the new-note form. Avoid a blank selection summary that requires choosing `Add log` or `History` before work begins.
3. Enter `Discussion` and `Next actions`. Keep `Meeting time` compact and use one primary `Save note` action. Show the follow-up choice near it.
4. Save with a clear acknowledgement, then continue to the next student without losing the list's search, filters, or position. Switching before saving should retain the draft.

Use a split layout only where both sides remain comfortably readable. The current table has a 64rem minimum width; putting a sidebar beside it without changing the columns would create horizontal scrolling. Start with fewer columns and validate the breakpoint. On smaller screens, use a student detail view with `Back to students`, rather than inserting a long form above the list.

Keep older meetings behind `Earlier notes` and phase changes behind `Phase history`. Profile changes should be available through `Edit details`. Archiving belongs with those secondary record actions, away from the note's primary save button. Preserve the existing list, phase, and Gantt capabilities, while testing whether the latter two need persistent top-level controls for this user's actual usage.

The concept demonstrates a stable desktop list, one-click note access, explicit follow-up states, and drafts that survive switching or closing students. It does not implement production draft storage, complete profile editing, phase/Gantt views, or calendar scheduling. Its past-target filter matches the intended subset; its meeting-attention filters exclude submitted students. Those are proposals to assess before changing production semantics.

Browser checks confirmed that the concept's first row starts at y=268 at both reviewed sizes and that all eight sample students fit in the initial viewport. Opening notes leaves the desktop table at the same position, with the save action visible at y=859. Switching Emma → Sofia → Emma retains the draft; saving updates the demo's last note while retaining the current follow-up. Search with no matches gives an explicit result message, and the past-target filter returns the expected three students. The narrow detail view has no horizontal overflow. The concept omits other application navigation and functions, so these measurements illustrate the layout direction rather than prove a production task-speed improvement.

Visible field labels, focus indicators, result counts, and save/error feedback remain useful in a personal tool. Removing help should reduce repeated narration without making form meaning depend on placeholders or memory.

## Visual direction

Use one neutral page surface, thin separators, compact spacing, and a single blue primary action. Aim initially for 14–15 px working text, 12–13 px supporting labels, 48–56 px list rows, and 36–40 px desktop controls. These are design starting points to check, not established optimums. Use larger touch controls on mobile and keep long notes comfortably readable.

Reduce the number of boxes before reducing the text size. Keep contrast strong: the current muted token `#6f7d8d` against white computes to approximately 4.21:1. For small text, that is below the 4.5:1 minimum described in [W3C's contrast guidance](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html). This is a specific token check, not a complete accessibility audit. Validate the new light and dark states in the local style guide and real student workspace. Compact controls should respect [W3C's target-size guidance](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html), including its size/spacing exceptions.

## Research basis

- Nielsen Norman Group's [minimalist-design guidance](https://www.nngroup.com/articles/aesthetic-minimalist-design/) recommends prioritizing information that supports the task and removing competing noise. Applying it here favors visible student records and notes over repeated descriptions.
- Its [table-task guidance](https://www.nngroup.com/articles/data-tables/) covers finding records, comparing values, editing a record, and taking action. It supports keeping the identifier first, placing relevant values together, and maintaining context when a record opens. The split workspace is our proposed application of those principles.
- Its [progressive-disclosure guidance](https://www.nngroup.com/articles/progressive-disclosure/) recommends keeping frequent functions immediately available and deferring rarely used options. Here, notes belong in the initial student view; phase audits and setup help can be secondary. Hiding the primary note form would work against that principle.
- [GOV.UK's text-input guidance](https://design-system.service.gov.uk/components/text-input/) supports short, visible labels and brief hints where they help someone answer. For this single regular user, broad onboarding sentences add little; save consequences and unusual derived values still need clarity.

These sources support design principles, not a measured speed improvement for this app. The claim that the current rounded, layered treatment feels dated comes from the user's feedback; the visual causes listed above are the reviewer's interpretation.

## Implementation sequence and validation

First fix draft loss and the close/reopen behavior. Next build the notes-first student workspace and compact cohort layout. Then simplify shared surfaces and copy, verifying the dashboard, mobile view, and style guide together. Correct the past-target filter when changing metric navigation. Reorganize settings after the frequent workflow works well.

Before shipping, try the following with the sole intended user, using the same realistic sample tasks on the current app and a working redesign:

- Open a known student, read the last agreed actions, and record a meeting note.
- Start a note, inspect another student, return, and continue the draft.
- Keep a booked follow-up, change it, and explicitly mark it not booked in separate saves.
- Close a student, reopen the same student, and continue with the same cohort filter.
- On a phone, find a student and record a short note without navigating through metrics.

Record task completion, time, extra clicks, accidental date/meeting changes, and lost drafts. The first release should require one activation to reach the note form, no lost drafts during record switching, an unchanged cohort position when desktop details open, and matching counts for quick filters. As an initial layout target, make the first student visible without scrolling at both reviewed viewport sizes. Compare actual task times before claiming the redesign is faster.
